# The renderer template bootstraps with no fix needed; a Japanese MSVC host loses Ninja header dependencies

- Date: 2026-10-04
- Version exercised: `ost 0.23.14`, renderer template 0.5.4, on a Windows 11
  workstation (MSVC 14.51, CMake 4.4.3, NVIDIA RTX A5000 with Vulkan API
  1.4.329, `VULKAN_SDK` 1.3.290), runtimes `cy2026-windows-x86_64-py313-core`
  and `…-lookdev` (OpenUSD 26.08)
- Occasion: creating `hydra-lotus` from the template
  ([PROJECT_LAYOUT.md §1](../../architecture/PROJECT_LAYOUT.md#1-what-the-project-is))
- Prior report: none here. The previous bootstrap from this template is
  `hydra-toon`'s
  [report 01](https://github.com/animu-sphere/hydra-toon/blob/main/docs/reports/ost/01-2026-09-26-v0.23.6-renderer-template-bootstrap.md)
  (`ost` 0.23.6, template 0.5.1), and that series' newest is
  [report 08](https://github.com/animu-sphere/hydra-toon/blob/main/docs/reports/ost/08-2026-09-30-v0.23.14-report-07-reverified.md)
- Next ask target: the next `ost` release

## TL;DR

**The template bootstraps a renderer that passes its whole contract with no
local fix: `core`, the `hydra` intent and the viewport each build, test and
validate on first run. One defect is new, and it is not visible in any
verdict: on a host whose MSVC prints Japanese, Ninja records no header
dependencies for some objects, so an edited header does not rebuild them.**

1. **Worked:** `ost init`, `ost build`, `ost test` and `ost validate` on
   `core` (3/3) and on the `hydra` intent (7/7, all thirteen renderer
   assertions `ok`), and `ost renderer viewport` (§1–§2).
2. **Resolved since `hydra-toon` report 01:** the template now compiles
   against OpenUSD 26.08, builds with `/utf-8`, and declares
   `frame.contexts: 1`; a no-op `ost build` and a viewport launch no longer
   fail `ost validate` (§2).
3. **P2: header dependencies are lost on a Japanese MSVC host** — in the
   `core` tree for the one source with a non-ASCII character, in the `hydra`
   tree for every Hydra source, in the viewport tree for every object (§3).

## 1. What was done

```sh
ost init --template renderer --name lotus --platform cy2026
ost build --jobs auto && ost test && ost validate
ost build && ost validate                                   # a no-op build
ost build --profile lookdev --intent hydra --jobs auto      # after declaring the intent
ost test --profile lookdev --intent hydra
ost validate --profile lookdev --intent hydra
ost renderer viewport -- --frames 8 --hidden
ost validate
ost validate --intent renderer-viewport
```

The `hydra` intent is project-declared in `openstrata.toml`
(`LOTUS_ENABLE_HYDRA2=ON`), as `hydra-toon` declares its own.

## 2. Worked

- `ost init` wrote 38 files plus `openstrata.toml` and
  `openstrata.scaffold.yaml`; `--name lotus` produced `Lotus`, `hdLotus`,
  `include/lotus/` and `LOTUS_` consistently.
- The `core` build took about 5 s. `renderer-report.json` recorded every GPU
  check PASS: 1,000 deterministic frames, colour and depth read back, no
  validation messages, device `NVIDIA RTX A5000`. `ost test` 3 of 3;
  `ost validate` passed, with the Hydra assertions explained `SKIP`s naming
  `LOTUS_ENABLE_HYDRA2`.
- A no-op `ost build` followed by `ost validate`: passed. `hydra-toon`
  report 01 §4.1 does not reproduce.
- The `hydra` intent: `ost test` 7 of 7, including
  `lotus-renderer-usdview-host` (3.8 s), and `ost validate` passed with all
  thirteen renderer assertions `ok`. The usdview first-frame and
  stable-update images were kept.
- `ost renderer viewport -- --frames 8 --hidden` fetched GLFW, built in
  `<target>--renderer-viewport`, and presented 8 frames with no swapchain
  recreation. Afterwards `ost validate` on the default target passed
  (`renderer-viewport — no durable viewport launch`, `SKIP`), and
  `ost validate --intent renderer-viewport` passed with `renderer-viewport`
  `ok`. `hydra-toon` report 01 §4.2 does not reproduce.
- None of `hydra-toon` report 01 §3's template defects is present:
  `renderer_plugin.cpp` branches on `HD_API_VERSION >= 98`, the MSVC options
  include `/utf-8`, and the manifest says `contexts: 1` with a comment that
  says what it counts.

## 3. P2 — Ninja records no header dependencies on a Japanese MSVC host

`ninja -t deps` in each build tree after the runs of §1:

| Tree | Objects with `#deps 0` |
| --- | --- |
| `cy2026-windows-x86_64-py313-core` | 1 of 5: `adapters/headless/…/main.cpp.obj` |
| `cy2026-windows-x86_64-py313-lookdev--hydra` | 5 of 9: `headless/main.cpp` and all four `adapters/hydra2/` sources |
| `cy2026-windows-x86_64-py313-core--renderer-viewport` | 28 of 28, GLFW's included |

An object with `#deps 0` is rebuilt when its own source changes and never
when a header it includes does. Nothing reports it: every build, test and
validation above passed. `hydra-toon` met the consequence in its renderer
reports 03, 09 and 10 — `toon-headless` crashing on a stale struct layout
after a core header edit — without a cause.

What was measured:

- CMake detected the `/showIncludes` prefix as `メモ: インクルード ファイル:`
  and wrote it to `rules.ninja` as `msvc_deps_prefix` in CP932. The build log
  shows the same prefix in UTF-8, echoed once per included header — Ninja
  passes through any line that does not match the prefix. In the `core` and
  `hydra` trees the echoed notes follow exactly the objects in the table.
- In the `core` tree the one affected source, `adapters/headless/main.cpp`,
  is also the one source containing a non-ASCII character: an em dash in the
  comment at line 270, three bytes in UTF-8. Replacing it with `--` and
  rebuilding gave that object `#deps 3`, and its include notes stopped
  appearing in the log. The other four sources are ASCII and kept their
  dependencies. So with `/utf-8`, MSVC printed the include notes in UTF-8
  for a source that contains non-ASCII text.
- The four Hydra sources are ASCII. What makes their notes UTF-8 — most
  likely non-ASCII text in an included OpenUSD header — was not established.
  Nor was why the viewport tree loses every object, including sources that
  keep their dependencies in the `core` tree.
- Setting `VSLANG=1033` for `ost build` on a fresh `core` tree changed
  nothing: the prefix was still detected in Japanese, and `main.cpp` still
  recorded no dependencies.

`/utf-8` is the fix `hydra-toon` report 01 §3.2 asked for, and it is right
for C4819. What it adds is that, on this host, the compiler's notes and
CMake's detected prefix stop agreeing.

This repository keeps `adapters/headless/main.cpp` ASCII-only, which fixes
the `core` tree. The `hydra` and viewport trees still need the workaround its
roadmap records.

**Asks:**

1. Keep the template's sources ASCII. That is the half of `hydra-toon`'s
   §3.2 ask the template did not take, and it fixes the `core` tree on its
   own.
2. Make the include-note prefix and the compiler's output agree on a
   non-English MSVC host — or, when `ost build` finishes on a Ninja tree,
   report objects whose dependency record is empty, so the loss shows up as
   a warning instead of a stale binary.

## 4. Observations, not asks

- **The workflow tree validates but is not tested.** After
  `ost renderer viewport`, `ost validate --intent renderer-viewport` reports
  `tested` and `renderer.install_tree` as `SKIP`. `hydra-toon`
  [report 08](https://github.com/animu-sphere/hydra-toon/blob/main/docs/reports/ost/08-2026-09-30-v0.23.14-report-07-reverified.md)
  §5 observed the same on its `hydra` workflow tree.
- **`.strata/targets/<target>/build.log` still accumulates across runs**
  (`hydra-toon` report 01 §6), which made the echoed-note count in §3
  unusable as a per-build measurement; `ninja -t deps` is the measurement.
- **The generated README ends with a "Workflow intent composition"
  paragraph** that reads as release notes for template 0.5.4 rather than as
  part of the project's README. This repository replaced the README with
  its own.
- **A `lookdev` build writes its own lock,**
  `strata.openstrata-cy2026-windows-x86_64-py313-lookdev.lock`, and leaves
  `strata.lock` on `core`. `hydra-toon` reports 02–03 saw a `lookdev` build
  rewrite `strata.lock`. Both locks record this workstation, so they are
  ignored here, as in `hydra-toon`.
- **`ost runtime list` shows the `core` runtime as source `mock`, validate
  `pending`.** Every build and validation on it passed, and `ost validate`
  reported `runtime-compatible` `ok`; nothing says what `pending` withholds.
