# Textures

Measured on 2026-10-06 in the working tree based on `755882d`, on Windows 11
x86_64 with MSVC 14.51, OpenStrata 0.23.14 and Release builds. The GPU was an
NVIDIA RTX A5000 (driver 597.16). Hydra used OpenUSD 26.08 lookdev and
CPython 3.13. All runs were local; hosted CI was not measured.

## Scope

The third slice of
[Renderer Phase 1.5](../roadmap/README.md#status-at-a-glance):
`UsdUVTexture` and `UsdPrimvarReader_float2` for the inputs the material IR
already translates (base colour, roughness, metallic and emission), which
needs texture coordinates in the GPU scene and texture residency. Normal
maps, opacity and the dielectric layer are later slices. The Cornell box
has no textures, so its committed reference images must be reproduced
exactly.

## Design

**The IR** (`include/lotus/material.hpp`). Each translated input gains an
optional `TextureInput`, UsdUVTexture's semantics without its node graph:
a texture key, the channel a scalar reads, the two wrap modes, scale, bias
and fallback. The material names one texture-coordinate set and its
fallback, as one `UsdPrimvarReader_float2` would. A `Texture` is decoded
texels in one of three formats (8-bit linear, 8-bit sRGB, 32-bit float),
four channels each, rows from the top. `LotusScene::textures` keys them like
materials, sharing their texels with retained snapshots.

**Texture coordinates** are geometry: `MeshGeometry::texcoords` maps a name
to one (s, t) per triangle corner, the layout authored normals already use.
Every float-pair set a mesh has is kept, so a material that changes which
set it reads rewrites only the instances. Each instance's set is resolved
by the update plan, as an index into the geometry's sets in key order.

**The update plan.** Textures are resident like geometry, identified by
address, uploaded and released in key order. The material table becomes
`SceneMaterial`s: each material with the resident texture each of its
lookups' keys names, so a texture edit rewrites the table even when the new
texture takes the old one's slot.

**The GPU scene.** One image per texture, `R8G8B8A8_UNORM`,
`R8G8B8A8_SRGB` or `R32G32B32A32_SFLOAT`, in the shader-read layout, with
a slot in a texture table of at most 1,024. The scene passes' descriptor set
gains a partially bound array of 1,024 sampled images, written per slot when
the table changes, and 16 immutable samplers, one per pair of wrap modes.
This is the bindless baseline of
[design policy §4.2](../design/DESIGN_POLICY.md#42-gpuscene). Partial
binding means a released slot's stale descriptor needs no rewrite, since no
material samples it. The instance record grows to 112 bytes with the set's
address and index. The material record grows to 304 bytes with one 64-byte
lookup per input, whose mode tells a constant from a lookup and from a
lookup whose key names no texture.

**The lookup** (`backend/vulkan/shaders/path_trace.slang`): bilinear at level
0, at (s, 1 − t), times scale plus bias, then clamped into the input's
range. A material without lookups reads no texture coordinates and takes
the constant path unchanged. There are no mipmaps: a path tracer has no
screen-space derivatives, and ray cones are later work.

**Diagnostics.** `SceneOutput::Albedo` and `SceneOutput::RoughnessMetallic`
write the hit's inputs after the lookups, the albedo and roughness AOVs of
[design policy §16](../design/DESIGN_POLICY.md#16-denoising). The normal
pass became a *surface pass* whose uniform block selects one of the three
outputs, so no pipeline was added.

**The adapter.** The translator follows `diffuseColor`, `roughness`,
`metallic` and `emissiveColor` to a `UsdUVTexture` and its `st` to a
`UsdPrimvarReader_float2` or a constant. It returns the texture requests,
which `AdapterState` decodes with Hio when the first material names a key
and removes when the last stops. One- and two-channel images expand as
Storm samples them. `HdLotusMesh` reads every float-pair primvar as a set
through the same corner expansion as normals, now one template for both.

## Findings

- **Profile upgrade.** slangc 1.4.350 warns, an error here, that
  `SampleLevel` on a texture array upgrades the `spirv_1_4` profile with a
  long list of capabilities, sparse residency among them. Declaring
  `-capability sm_5_0 -capability spvShaderNonUniformEXT` silences it. The
  module still declares only `Shader`, `Int64`, `RayQueryKHR`,
  `PhysicalStorageBufferAddresses` and `ShaderNonUniform`, checked with
  `spirv-dis`.
- **Colour space through UsdImaging.** OpenUSD 26.08 hands a
  `UsdUVTexture`'s `sourceColorSpace` to Hydra as the `colorSpace:file`
  parameter, not as `sourceColorSpace`. The translator reads either; the
  stage test's `raw` image found it.
- **sRGB decoding on the device.** Against an exact decode before
  filtering, the RTX A5000 decodes sRGB texels within about 0.7% of the
  value: a constant texel of 200 gave 0.57758 ± 0.00054, and near white the
  error reached 0.004. Linear and float textures stayed within a quarter of
  the error that 8-bit subtexel weights allow. The oracle's tolerance is
  2⁻⁷ of the four texels' spread plus, for sRGB colour, 1% of the larger
  texel.

## Verification of the slice

**The lookup diagnostics** (`renderer.path.textures`, first part). An
orthographic view holds five meshes. Each pixel centre is compared with an
oracle in the headless runner: Vulkan's bilinear filter and address modes
in double precision, sRGB decoded before filtering. It shares no code with
the shader. Pixels within 0.02 of a triangle edge are skipped.

| Mesh | Lookups | Pixels (albedo / roughness and metallic) |
| --- | --- | --- |
| `/repeat` | a 4×4 sRGB texture, repeat × mirror, over st in [−0.6, 1.7] × [−0.4, 1.3]; then roughness from the green of a 3×2 linear texture scaled by 1.5 (mirror × repeat) and metallic from its alpha biased by −0.125 | 756 / 756 |
| `/clamp` | the sRGB texture, clamp × black border, green scaled by 0.5 and biased by 0.25; then metallic from its red | 756 / 756 |
| `/float` | a 2×3 float texture through the second of two sets, values pushed out of [0, 1] by scale and bias | 756 / 756 |
| `/missing` | a key with no texture: the fallback, for colour and for alpha | 378 / 378 |
| `/unmapped` | a mesh without the material's set: the texture-coordinate fallback | 356 / 356 |

The sRGB texture is then replaced with its columns mirrored, and the albedo
is compared again: the edit reaches the device through a new image and a
rewritten descriptor.

**Textured radiance** (`renderer.path.textures`, second part). A Lambert
square fills the view under a white environment. It has an 8×8 albedo
texture and an 8×8 float emission texture, both of 2×2 blocks of 4×4
texels. Within a block, half a texel from its edges, the filter is
constant, so every sample there reflects its block's albedo exactly and
adds its emission. With 4 samples per pixel, the 2,304 such pixels matched
albedo + emission within 10⁻⁶ + 10⁻⁴ relative, and with no bounces the
emission alone.

**The GPU scene.** `renderer.scene.upload` adds three steps:

- texture insertion: an sRGB and a float texture, a geometry with two sets,
  and a material with a lookup of each plus one of a missing key;
- texture edit: one release and one upload, the table rewritten, no
  instance;
- texture removal.

After each, the read-back images, sets, instance sets and material lookups
(slots resolved by texel content) must match the CPU scene.

**The reference, bit for bit.** `renderer.path.reference` reports that the
reference's samples reproduce the committed mean bit for bit, and
`lotus-headless --write-reference` after the final build wrote mean and
variance byte-identical to `validation/reference/`.

**Hydra.** `lotus-renderer-hydra-texture` translates hand-built networks:

- a primvar reader's set and fallback;
- a scalar channel;
- an unresolved asset, kept by its authored path;
- `useMetadata` as black, and a `colorSpace:file` linear space as raw;
- a colour output on a scalar input, and a second texture-coordinate
  source, both untranslated;
- a texture without a file.

It then writes PNGs with Hio and syncs a stage through UsdImaging. The
stage's 8-bit RGB image must decode as sRGB under `auto` and linear under
`raw`, with an opaque alpha, and a one-channel image as grey. A missing
image leaves its key without a texture. The face-varying indexed `st` and a
vertex `map1` must reach every corner. Then:

- a wrap edit re-translates the material without decoding its image again;
- a file edit swaps only that lookup's image;
- a primvar edit replaces the coordinates;
- removing a material releases exactly the images only it named.

The `-gpu` variant renders the colour AOV, whose clamped corner pixels must
show their texels' albedo plus the missing emission image's fallback.
`lotus-renderer-hydra-material` now expects its `diffuseColor` texture
connection to be translated.

## Fault injections

Each was reverted, and the sources touched, before the runs below.

| Fault | Caught by |
| --- | --- |
| Lookups at (s, t) instead of (s, 1 − t) | `renderer.path.textures` (albedo (0.244, 0.308, 0.232) instead of (0.155, 0.335, 0.421)) |
| sRGB textures uploaded as `R8G8B8A8_UNORM` | `renderer.path.textures` (albedo (0.375, 0.533, 0.575) instead of (0.155, 0.335, 0.421)) |
| The sampler index swaps the wrap modes | `renderer.path.textures` and `renderer.scene.upload` (texture insertion) |
| Instances read their geometry's first set | `renderer.path.textures` (the float texture's pixels) |
| Lookups ignore scale and bias | `renderer.path.textures` (green 0 instead of 0.25 on `/clamp`) |
| Emission lookups are ignored | `renderer.path.textures` (radiance 0.749 instead of 1.249) |
| One-channel images expand to (r, 0, 0, 1) | `lotus-renderer-hydra-texture` and `-gpu` ("the one-channel image was not expanded to grey") |
| Face-varying coordinates are not triangulated | `lotus-renderer-hydra-texture` and `-gpu` ("the quad's texture-coordinate sets differ") |

## Verification

Before the builds, `ninja -t deps` listed objects without recorded header
dependencies, the known Japanese-MSVC issue
([roadmap](../reference/SUPPORTED_CONFIGURATIONS.md#build-and-tooling-limitations)); they were
deleted before each build.

- `ost build --jobs auto`, `ost test`: **8/8 passed**;
  `ost validate --strict-renderer-evidence`: **passed**, with
  `renderer.path.textures` new, `.path.reference` and `.scene.upload` PASS
  and zero Vulkan validation messages.
- `ost build --without-runtime --intent ci-core --jobs auto`,
  `ost test --without-runtime --intent ci-core`: **8/8 passed**.
- `ost build --profile lookdev --intent hydra --jobs auto`,
  `ost test --profile lookdev --intent hydra`: **23/23 passed**, with
  `lotus-renderer-hydra-texture` and `-texture-gpu` new;
  `ost validate --profile lookdev --intent hydra --strict-renderer-evidence`:
  **passed**.
- `ost renderer viewport -- --frames 8 --hidden`: presented 8 frames;
  `ost validate --intent renderer-viewport`: **passed**.
